## 0. このドキュメントの位置づけ

`requirements.md` が定義する既存の「シナリオ売上分析」（Lステップのタグ進捗×広告クエリを案件全体のKPIとして集計するもの）とは**別軸**の機能。こちらは**クリエイティブ（広告素材）単位**で「実際にいくらのCVを・いくらの費用で獲れているか」を可視化する。

0813renewal.mdの方法論の核心は下記の一点に尽きる。

> 遷移先URLに `?ad-creative-id=〇〇` を仕込み、①広告配信実績RAWDATA（媒体側）と ②クリエイティブ単位で紐づけている実CVのRAWDATA（自社側）を、このキーで突合する。

この突合さえ成立すれば、あとはUI・グラフ・フィルタ・画像分析・LP分析は好きに拡張できる（0813renewal.md本文より）。**逆に言えば、この突合が成立しない限り本機能は着手できない。**

## 1. 前提条件（最重要・現時点で未充足）

2026-08-13時点の調査結果:

| 項目 | 現状 | 判定 |
|---|---|---|
| ECP `ads` RAWDATA | `config/ecp/config.yaml` の `daily_kpi`/`weekly_dashboard.ads` は検索語句レポート相当（日付・クリック・表示回数・費用・コンバージョンのみ）。クリエイティブ単位の列・遷移先URL列は無し | ❌ 未充足 |
| STD `ads` RAWDATA | `config/std/config.yaml` も同様に検索語句レポート相当 | ❌ 未充足 |
| 実CV RAWDATAの「流入元URL」列 | ECP/STDともに管理表・Lステップエクスポートに該当列なし（管理表は集計値、Lステップは友だち単位のタグ進捗のみ） | ❌ 未充足 |
| `?ad-creative-id=` のようなURLパラメータ運用 | リポジトリ全体・両案件のconfig・ドキュメントいずれにも記載なし | ❌ 未充足 |
| クリエイティブ画像のGoogleドライブ格納（ファイル名＝広告名） | `drive.folder_id` はCSV/PDF置き場としてのみ運用確認済み。クリエイティブ画像フォルダの存在・命名規則は未確認 | ❓ 要確認 |

**結論: 本機能はデータ基盤がゼロから必要。着手前にクライアント側（伊藤さん等）への確認・データ整備依頼が必須。**

### 1.1 確認・整備が必要な事項（クライアント確認リスト）

1. **媒体側**: ECP/STDそれぞれの広告アカウント（Meta/Google等）で、クリエイティブ（広告）単位の配信実績（インプレッション・クリック・費用）と**遷移先URL**をエクスポートできるか。GASでMarketing API等から日次収集する仕組みを新設できるか（0813renewal.mdの前提と同じ構成）。
2. **自社側（実CV）**: 決済・問診・診察のどのシステムが「流入元URL」を記録しているか。現行タグ設計（`診察誘導_STEP*`・購入タグ等）はLINE内の行動タグであり、**広告からの遷移URLそのものは保持していない**。決済システム側のログにURLパラメータが残るか、Lステップの友だち追加URL/リッチメニュー遷移URLにパラメータを載せられるかの確認が必要。
3. **`?ad-creative-id=` 運用**: 入稿URL単位でパラメータ値を変える運用（一意性担保）を誰が行うか。現在ECP/STDの広告入稿は誰が最終URLを設定しているか（媒体担当・伊藤さん・広告代理店等）。
4. **クリエイティブ画像**: Googleドライブにクリエイティブ画像を「ファイル名＝広告名」で格納する運用が可能か（F3の前提）。
5. **LP一覧**: 遷移先URLからLPのURLを収集する前提上、LPのバリエーション数・URL構造（パラメータ付与でLP自体は変わらないか）を確認。

上記が確認・整備されるまで、本仕様書は「実装できる形の設計案」を示すに留め、実装（Phase 1以降）には着手しない。

## 2. RAWDATAスキーマ案

0813renewal.mdの2種のRAWDATAを、既存config（`config/<project>/config.yaml`）の命名規則に合わせて具体化する案。

### 2.1 `creative_ads`（広告配信実績・クリエイティブ単位）

| フィールド | 説明 |
|---|---|
| `date` | 配信日 |
| `platform` | Meta / Google 等の媒体 |
| `account` | 広告アカウント |
| `campaign` | キャンペーン名 |
| `ad_set` | 広告セット／広告グループ |
| `ad_name` | 広告（クリエイティブ）名。**Googleドライブ上の画像ファイル名と一致させる運用が前提**（0813renewal.md） |
| `impressions` / `clicks` / `cost` | 基本指標。CTR・CVRはローカルで計算し収集しない（0813renewal.md方針踏襲） |
| `destination_url` | 遷移先URL。`?ad-creative-id=〇〇` を含む |

### 2.2 `creative_conversions`（クリエイティブ単位の実CV・自社側）

| フィールド | 説明 |
|---|---|
| `conversion_date` | 実CV発生日 |
| `referrer_url` | 流入元URL。`?ad-creative-id=〇〇` を含む（`creative_ads.destination_url` と同一パラメータで突合） |
| `product` | 購入商品（ECP: 72h/120hの1回分・2回分、STDは商品別CVタグに準拠） |
| `revenue` | 実売上額 |

### 2.3 突合キー

`destination_url` / `referrer_url` から正規表現 `[?&]ad-creative-id=([^&]+)` で `creative_id` を抽出し、`creative_ads.creative_id = creative_conversions.creative_id` でjoinする。**一意性はクリエイティブ入稿URL単位で保証する運用が前提**（同一クリエイティブでもLP/訴求が変われば別ID、という粒度は今後要確認）。

## 3. 機能要件（0813renewal.mdの4機能をECP/STD向けに翻訳）

| ID | 機能 | 内容 |
|---|---|---|
| F1 | クリエイティブ別実CPAテーブル | クリエイティブごとの実CV数・実CPAを一覧表示。媒体・アカウント・キャンペーン・広告セットでフィルタ |
| F2 | 費用・実CPA日別推移グラフ | クリエイティブ単位で費用と実CPAの日次推移を可視化。予算増額判断の材料 |
| F3 | 勝ち/負けクリエイティブの画像分析 | Googleドライブの画像を`ad_name`で突合→勝ちCR群・負けCR群それぞれの共通要素をLLMで分析しレポート化。UIのボタン起動（手動実行） |
| F4 | LP分析 | `destination_url`からLP URLを収集→スクリーンショット→LPの構成・訴求内容をまとめて一覧表示。ボタン起動時に新規LPを自動検知し追加処理 |

いずれも0813renewal.md本文の記載通り、**F3/F4は手動実行（ボタン起動）**とする。全量自動化ではなく、必要なタイミングで担当者が起動する運用を踏襲する。

## 4. アーキテクチャ配置（案）

現行revenue-analyzerは2系統が併存する。

- **Next.js Webアプリ**（`src/app`, `src/lib/*`）: STD/dayvigo向け。CSVアップロード→ブラウザ内集計というインタラクティブUI。
- **Pythonバッチパイプライン**（`scripts/daily_kpi`, `scripts/weekly_dashboard`）: ECP向け。Google Driveから定期取得しGoogle Sheetsへ同期するバッチ運用。

0813renewal.mdが描く体験（「見やすいUIでフィルタ」「ボタンクリックで画像分析・LP分析を起動」）はインタラクティブなWebアプリに近い。そのため、**Next.js Webアプリ側に新モジュールとして追加する案**を第一候補とする。

- 設定: `config/<project>/creative_cpa.yaml` を新設（案件ごとにON/OFF・列マッピング・媒体種別を設定可能にし、既存の「案件追加は設定ファイルのみ」方針を踏襲）。
- 取込・突合: `src/lib/creative/`（ingest・join・aggregate）
- 画面: 既存 `AnalyzerClient.tsx` に新タブとして追加、またはF1/F2用の新規ページ
- 画像分析・LP分析: サーバーサイド処理（Next.js API route）としてGoogleドライブAPI・Claude API（Vision）・スクリーンショット取得（要ライブラリ選定）を呼び出す。現状 `package.json` に該当依存（googleapis / Anthropic SDK / Playwright等）は無く、Phase 3/4着手時に追加要否を判断・ユーザー確認する。

**代替案**: ECP側は既存Pythonバッチ資産（`gspread`/`google-auth`導入済み）に寄せ、Google Sheets上でクリエイティブ別CPA表を提供する案もある。ECPとSTDで別アーキテクチャになる非対称性はあるが、ECPの既存運用（Sheets同期）とは親和性が高い。**この判断は次回Phase 1着手時に確定する。**

## 6. 既存機能との違い（要注意）

`requirements.md` §F5〜F7の「広告クエリ分析」「統合分析」は**検索語句単位**かつ**Lステップのタグ進捗による近似マッチ**（Phase 1アトリビューション）である。本仕様書が扱う「クリエイティブ単位実CPA分析」は**クリエイティブ単位**かつ**URLパラメータによる厳密突合**であり、精度・粒度ともに上位互換だが、その分**データ整備コストが高い**（§1参照）。両者は排他ではなく併存する別機能として位置づける。

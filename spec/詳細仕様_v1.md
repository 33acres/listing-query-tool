## 2. データモデル（正規化後の標準スキーマ）

### 2.1 LstepFriend（友だち1件＝1レコード／集計専用・非表示）
| 標準フィールド | 型 | 説明 |
|---|---|---|
| `userId` | string | 集計キーのみ。**画面・レポート・保存物に出さない**。必要なら即ハッシュ |
| `mark` | string | 対応マーク（例: 未対応/決済案内済み/発送済/定期便契約中…） |
| `addedAt` | Date | 友だち追加日時 |
| `lastActionAt` | Date \| null | 最終アクション日 |
| `appliedViaStep` | string \| null | 申込経由STEP（ラストタッチ） |
| `steps` | Set<string> | 押下済みCTAタグ集合（例: STEP0A, STEP1…）|
| `paymentClicks` | { tanpin: bool, teiki: bool } | 決済クリック有無 |
| `purchases` | Set<string> | 購入タグ集合（teiki/tanpin_1m/3m/6m 等） |
| `status` | { paid, monshinSubmitted, shinsatsuDone, shipped } | 各bool（導出方法は§4.1） |
| `step0Branch` | string \| null | STD: 治療希望/検査希望 |

### 2.2 AdQuery（既存 listing-query-tool の型を流用）
`date, searchQuery, impressions, clicks, cost, conversions, cvValue?, campaign?, adGroup?, keyword?` → 集計で `cpa, ctr, cvr, roas` を算出。

### 2.3 RsaAsset（将来）
`date, assetType(headline/description), assetText, impressions, clicks, conversions`。

### 2.4 個人情報ホワイトリスト（実装必須）
- 取り込み時、**標準スキーマに定義された列のみ**を採用。`config.column_mapping` に無い列は破棄。
- `drop_pii` に列挙された列（例: `表示名`）は明示的に破棄。氏名・電話・メール・住所に該当しうる列は採用しない。
- `userId` 以外の個人特定値はメモリにも載せない。`userId` は突合後に破棄可能なら破棄。
- すべての出力（画面/Markdown/HTML/ファイル）は**集計値のみ**。1人1行のリスト描画を禁止（実装上、個票レンダリングのコンポーネントを作らない）。

## 3. 取り込み・正規化

### 3.1 CSVパース
- `papaparse` ＋ `encoding-japanese`。Shift_JIS / UTF-8 自動判定。
- 数値の桁区切り（`"15,000"`）・全角空白・前後空白を吸収。
- 日付は `YYYY-MM-DD HH:mm:ss` / `YYY/MM/DD` 等を吸収し `Date` へ正規化（`date_utils`）。

### 3.2 列マッピング
- `config.column_mapping` で「標準フィールド → CSV実列名」を解決。
- タグ系（`steps` / `purchases` / `paymentClicks`）はセル値が `1` または非空なら true。
- 未マッピング列・`drop_pii` 列は破棄（§2.4）。

### 3.3 期間フィルタ
- 新フロー集計の起点 `flow.new_flow_start`（例 2026-04-29）を config に持つ。
- 集計期間（当期/前期）はUIで選択。広告分析は当期 vs 前期で比較。

## 4. 分析ロジック

### 4.1 ファネル（新フロー・売上ファネル）
新フロー: `LINE登録 → 決済 → 問診票提出 → ビデオ診察 → 発送`。各ステップの判定は**案件で導出方法が異なる**（重要）。

| ステップ | dayvigo（対応マーク中心） | STD（共通タグ中心） |
|---|---|---|
| ① LINE登録 | 期間内の全レコード | 同左 |
| ② 診察スタート | `steps` に STEP0A or STEP0B | `step0Branch == 治療希望`（or STEP0A） |
| ③ STEP1到達 | `steps` に STEP1 | 同左 |
| ④ 決済クリック | `paymentClicks.tanpin or teiki` | 同左 |
| ⑤ 決済完了 | `purchases` が非空 **or** `mark` が購入系（発送済/定期便契約中/昨日決済 等） | `status.paid`（`決済済み`タグ）**or** `purchases` 非空 |
| ⑥ 問診票提出 | `mark` が「問診提出済み」系 ／ ⚠タグ無し（**TBD**） | `status.monshinSubmitted`（`問診票提出済み`タグ） |
| ⑦ 診察完了 | **TBD**（マーク/タグ未確定） | `status.shinsatsuDone`（`診察完了`タグ） |
| ⑧ 発送 | `mark == 発送済 / 今日発送済み / 定期便契約中(縛り)発送済み` | `mark == 発送済` |

- **転換率**: 各ステップ人数 ÷ 前ステップ人数（①基準の通過率も併記）。
- **要フォロー層を必ず明示**: 「決済済み × 問診票未提出」（dayvigo の `mark` 例: `デエビゴ定期 昨日決済(新問診票未提出)`、STD: `決済済み AND NOT 問診票提出済み`）。
- ステータス導出ルールは `config.status_rules`（マーク値リスト/タグ名）で外出しする。⑥⑦のdayvigo定義は確定後 config 差し替え。

### 4.2 月別KPI / 定期率 / 週次（既存KPI Excel移植）
- 月別: 新規登録数・決済完了数（定期/単品1/3/6ヶ月）・CVR（決済÷登録）・定期率（定期÷決済）・前月比。新旧フロー区別。
- 定期率 = 定期購入数 ÷ 決済完了数。単品内訳（1/3/6ヶ月）を併記。
- 週次: 週（月曜起点）ごとの登録数・決済数・定期率。
- ※分母定義は既存Excelに準拠（§10で要確認）。

### 4.3 STEP別 申込貢献分析
- 各STEPの貢献 = `count(steps∋STEPn AND status.paid)`。
- **全タッチ**（`steps` 追記式＝複数STEP可）と**ラストタッチ**（`appliedViaStep`）の両軸で集計。
- 出力: STEP別 申込数・申込率（÷そのSTEP到達者）・ラストタッチ分布。

### 4.4 シナリオ価値スコア
- 対象シナリオは `config.scenarios`（案件別固定2本）。
- 指標: 到達数 / クリック率（CTAタグ押下率）/ CV率 / 売上貢献率。開封率・ブロック率は**取得しない**（欠損は「未計測」表示）。
- スコア式（重みは `config.scoring.scenario`）:
  `Score = CV率×35 + クリック率×20 + 売上貢献率×25 + CV速度×10 − ブロック率×20`
  （ブロック率は未計測のため係数0で運用＝実質 `CV率×35 + クリック率×20 + 売上貢献率×25 + CV速度×10`）。
- ⚠**制約**: 友だちCSVにシナリオ変種（15分後 / 時刻21時指定）を識別する列が無い場合、シナリオ単位の分割は不可。その場合は**STEP貢献（§4.3）と全体ファネルにフォールバック**し、レポートに明記（§10）。

### 4.5 広告クエリ分析（既存ロジックを流用）
既存 `src/lib/classifyQueries.ts` / `scoring.ts` / `aggregateQueries.ts` / `comparePeriods.ts` をそのまま使う。
- 母数不足閾値（既存値）: clicks<10 / cost<3000 / impressions<100 / 当期+前期clicks<20 → 監視。
- 無駄クエリ: `CV=0 かつ cost≥10000 かつ clicks≥20`、または `当期cost>前期 かつ 両期CV=0 かつ 合計cost≥15000`。
- 分類: 勝ち / 悪化 / 無駄 / 機会損失 / 新規 / 消滅 / 監視 / 要確認（保護ワード）。
- 保護ワード: `config.protected_words`（例: デエビゴ / 指名 / ブランド名）。
- 優先度スコア: 既存 `calcPriorityScore`（CV減少+費用悪化+CPA悪化+機会損失）。
- **RSA分析（新規・データがあれば）**: 見出し別 表示/CTR/CVR、勝ち訴求・釣り訴求（CTR高CV低）・露出不足（CV高CTR低）の判定。

### 4.6 統合分析（核）
- 接続キー（Phase 1・近似）: 広告クエリ集計（当期）×流入規模 と Lステップ流入数・シナリオ反応・CV・売上を**期間軸で突合**。
- ⚠gclid/utmが友だちCSVに無いため、**クエリ単位の厳密な売上接続は不可**。MVPは「クエリ群の傾向」と「LINE側の反応・CV・売上」を**同一期間で並置**し、相関を示唆として提示（厳密接続はPhase 2/3）。
- 出力表: 流入規模 / 反応STEP / CV率 / 売上 / 判断（強化・除外検討・LP改善 等）。

### 4.7 売上推定
- `revenue = Σ count(購入タグ_i) × unit_price_i`（`config.pricing`）。
- dayvigo: 定期=初回2,980 / 単品1ヶ月=9,680 / 3ヶ月=22,396（一括）/ 6ヶ月=40,348（一括）。**LTVは扱わない**。
- STD: 治療薬=8,140 / 検査キット 9,900〜28,000。**商品レベルのタグ識別はTBD**（§10）。確定まで「治療薬基本線」or「決済済み×平均単価」で概算し、概算である旨を表示。
- 粗利（STDは原価判明）: `売価 − 原価 − 送料310 − 梱包20 − 決済手数料2.65%`。**将来拡張**。

### 4.8 ルールベース改善提案
| 状態 | 提案 |
|---|---|
| 費用高・CV0 | 除外候補 |
| CTR高・CV低 | 訴求とLPのズレ |
| CV高・CPA低 | 強化候補 |
| 表示多・CTR低 | 広告文改善 |
| STEP: CTA押下多・CV低 | 遷移先/決済導線改善 |
| ファネル: 決済済み×問診未提出 多 | リマインド延伸（15分→1時間→翌日） |

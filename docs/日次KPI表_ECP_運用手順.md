## 1. 実行手順

### ① Driveから当日分をダウンロードして raw に置く

```
output/ecp/<実行日>/raw/
├── アフターピル全体管理【あしたのクリニック】 - YYYYMM.csv   （複数月ぶんでOK）
├── アフターピル全体管理【あしたのクリニック】 - YYYYMMDD.csv （当月・最新版）
├── lstep2022.csv 〜 lstep2025.csv                            （年別・据え置きでOK）
└── lstep<YYYYMMDD>.csv                                       （最新の全量エクスポート）
```

- 管理表は **CSV または XLSX** で出す。⚠️ ECPの管理表PDFは未対応（エラーで止まる）。
  PDF読み取りはSTDの列順に合わせた実装で、ECPは列構成が違う（商品別CV列が無く
  `実CV` 1本）ため、黙ってずれた数値を出さないよう失敗させている
- Lステップは **年別に分割されていてもよい**。`lstep*.csv` を全部拾ってIDで重複排除する
- ⚠️ Lステップは必ず **全量エクスポート**（期間指定・タグ絞り込みなし）

### ② 実行

```bash
cd /Users/yuya/onemedical/revenue-analyzer
.venv/bin/python -m scripts.daily_kpi.main --project ecp --run-date 2026-07-28
```

`--run-date` は **データを取得した日**を入れる（コホート成熟度の基準日になる）。

### ③ 出力を見る

| ファイル | 中身 |
|---|---|
| `daily_bottleneck_report.md` | まずこれを読む。判定・区間別・日次表・Cost帯別・突合結果 |
| `daily_kpi.csv` | 日次KPI表（管理表×Lステップ突合済みの全列） |
| `daily_bottleneck.csv` | 区間別の悪化幅・判定・アラート（日ごと） |
| `daily_kpi_history.csv` | 全期間の追記履歴（`output/ecp/` 直下・再実行で同一日は上書き） |
| `daily_kpi_meta.json` | 入力ファイルのSHA256と判定可能範囲（監査用） |

Google Sheetsへ反映したいときだけ `--sync-sheets` を付ける（`DailyKPI` /
`DailyBottleneck` タブを毎回洗い替え）。付けなければ外部への書き込みは一切しない。

## 2. 表の読み方

### ファネルは4段（STDの5段とは違う）

```
広告クリック(CTs) → LINE登録(CV(F)) → 事前決済クリック → 購入(実CV)
```

ECPは管理表の `問診回答` が全日0（問診票を経由しないフロー）なので、STDの
「問診回答」段は存在しない。

### 時間軸が3種類あるので混ぜて読まない

| 表記 | 意味 |
|---|---|
| 当日軸 | 分子・分母とも管理表の同日実績。素直に日次で読める |
| コホート軸 | Lステップの友だち追加日基準の到達率。「7/21に登録した人が、その後いつか決済リンクを踏んだ率」 |
| 混在軸 | 分母がコホート軸・分子が当日実績。ECPは即日購入に寄るため近似として使えるが、単日では100%を超える日もある。移動平均で読む |

### 自動判定のしくみ

- 区間CVR(7日) = 直近7日の**分子合計 ÷ 分母合計**（比率の平均ではない。単日CV数件の
  日に引っ張られないため）
- ベースライン = その7日窓の**直前28日**の同じ計算
- 差分が **-2.0pt 以下**なら `🔴 悪化確定`、それ未満の低下は `🟡 誤差範囲`
- 窓から自動的に除外される日
  - **コホート未成熟日**（友だち追加から3日未満。まだタグが付き終わっていない）
  - **タグ運用開始前の日**（付与率が継続して立ち上がった日を自動検出。ECPは
    2026-07-03以降が比較可能範囲）

### CVRトレンドとは別の単日アラート

| 内容 | 閾値 |
|---|---|
| 出稿注意 / 出稿過多 | 1日Cost 45万円 / 60万円 |
| 垂直粗利マイナス | 0円未満 |
| 粗利率低下 | 20%未満 |
| 突合乖離 | 管理表CV(F)とLステップ登録数の差が5%超 |

閾値は `config/ecp/config.yaml` の `daily_kpi.guardrails` で変更できる。

## 3. 現時点で計測できないこと

| 項目 | 状態 |
|---|---|
| `ECP_決済済み` タグ | 列はあるが**全件0件**（決済システム→Lステップ連携が未実装）。購入の個人単位紐付けは不可 |
| `ECP_問診票提出済み` / `ECP_診察完了` / `ECP_発送済み` | エクスポートに列が存在しない。診察完了率・発送リードタイムは計測不能 |
| `ECP_処方可_*` | 列が存在しない。「処方可なのに買わなかった」母数が取れない |
| 日別キャンペーン実績 | `ads.csv` は検索語句レポートのみ。出稿上限をキャンペーン単位で管理するには日別キャンペーンレポートの追加取得が必要 |

決済タグ連携が入れば、③の区間が混在軸から純粋なコホート軸になり、
「登録した人が買ったか」を個人単位で追えるようになる。

## 4. 他プロジェクトへの流用

`config/<project>/config.yaml` に `daily_kpi` ブロックと実列名の
`management.column_aliases` を用意すれば、同じコマンドでSTD・dayvigoにも使える
（ファネルの段は `scripts/daily_kpi/kpi.py` の `STAGES` を診療科に合わせて調整する）。
